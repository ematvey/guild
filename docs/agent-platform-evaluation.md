# Guild agent platform evaluation

**Decision.** Use standalone agentgateway first if Guild needs provider failover, shared network policy, or standardized model telemetry. Evaluate Agent Substrate as a replacement for the server-side sandbox runner when distributed execution or idle sandbox density warrants Kubernetes. Use kagent for a catalog of operator-managed specialist workers if there is demand for that catalog. Keep the Guild harness for interactive chats and the personal Assistant.

The products work at different boundaries. Agent Substrate schedules and isolates compute. kagent v1 supplies an agent and session control plane on Agent Substrate. agentgateway proxies model, MCP, and A2A traffic and can run in the existing Compose stack. Adopting all three is optional. [Agent Substrate](https://github.com/agent-substrate/substrate), [kagent architecture](https://kagent.dev/docs/kagent/latest/about/architecture/kagent/), [agentgateway standalone](https://agentgateway.dev/docs/standalone/latest/)

## What Guild owns today

- **Model traffic.** The cloud harness registers an org-specific loopback provider. Guild exposes OpenAI-compatible and Anthropic endpoints, resolves org models and keys, enforces monthly USD quotas, hydrates media references, adapts streams, and writes usage and traces. The same model catalog and gateway contracts serve clients. - **Tool execution.** Guild's executor selects an agent workspace sandbox, a plain-chat sandbox, or a paired member machine. The Substrate actor workers create gVisor sandboxes. Agent workspace containers serve multiple threads and use the shared JuiceFS volume. Plain chats have their own target. The Guild harness owns CodeMode, approval classification and remote machine routing. ## agentgateway

**Recommended scope.** Insert it between Guild's existing dispatch/provider adapter and a few upstream models. Guild remains the authority for model aliases, per-org routes and credential admission, monthly USD quotas, member/thread attribution and trace IDs. The first iteration can use a static route or narrow opt-in mapping, leaving existing upstreams available for rollback. Keep the current public OpenAI and Anthropic endpoint behaviors, including streamed errors and terminal events. The lowest estimate assumes deploy/config plus focused tests.

The larger option moves upstream credential handling, routing and protocol translation into agentgateway, while retaining a Guild compatibility and accounting layer. A Guild route update currently writes to Guild's database. For day-two parity, propagate desired config to the gateway, verify the effective revision, and define how a rejected update, disabled route or rotated secret affects admission. Reconcile organization and provider identity in telemetry, especially when routes fail over. Agentgateway has native model formats, traffic policy, OTel and local or distributed rate limits. Local counters are replica-local and ephemeral. Standalone also offers per-key cost limits with response-time charging. Guild's existing quota and billing behavior needs an explicit parity check before moving authority. [Introduction](https://agentgateway.dev/docs/standalone/latest/documentation/about/introduction/), [config updates](https://agentgateway.dev/docs/standalone/latest/documentation/setup/update/), [rate limits](https://agentgateway.dev/docs/standalone/latest/documentation/configuration/resiliency/rate-limits/), [cost controls](https://agentgateway.dev/docs/standalone/latest/documentation/llm/cost-controls/budget-limits/)

MCP federation is an independent option for a controlled set of shared connectors. Guild can keep its connector names and tool classification above that boundary. Personal MCP connections use encrypted credentials re-resolved at invocation, with current availability checked; Guild also applies its own interactive approval rules. Preserve per-member authentication and revocation, tool naming, and call policy across a proxy. Leave automatic retries off for side-effecting tools, and verify behavior when an upstream stream fails after output has begun. [Personal MCP](../apps/server/src/harness/user-mcp.ts), [org MCP](../apps/server/src/integrations/org-mcp.ts), [MCP authentication](https://agentgateway.dev/docs/standalone/latest/documentation/configuration/security/mcp-authn/), [retry policy](https://agentgateway.dev/docs/standalone/latest/documentation/configuration/resiliency/retries/)

Sizing for standard model-plane adoption assumes about 450–1,100 lines for config and identity projection, 450–1,100 for compatibility and accounting adapters, and 500–1,300 for tests and rollout wiring. Most deletions come from provider adapters and duplicated upstream normalization. Upstream translation and SSE support still need representative tests for tool-call deltas and IDs, usage/cache fields, media, custom OpenAI-compatible models, cancellation and errors. The meaningful comparison is latency to first token, failover success, and audit parity against a direct Guild route.

## Agent Substrate

**Recommended scope.** Target Guild's existing sandbox interface. Use a small authenticated bridge to provision and address Actors, retain the sandbox-side tool/file service initially, and preserve a stable sandbox identity per agent workspace. A plain chat can use a separate Actor. Preserve the existing shared workspace topology or design a dedicated file service before migrating agent workspaces. Guild also needs file reads and downloads while an Actor sleeps. Substrate lists external CSI volumes as a preview feature with Actor-specific provisioning and lifetime. Validate an independent shared workspace path before cutover. [Workspace reader](../apps/server/src/agents/workspace-fs.ts), [CSI volumes](https://ate.dev/docs/guides/csi-volumes/) A first pilot with plain chats isolates the runner change from shared-agent workspace migration.

Substrate provisions Workers ahead of demand, schedules Actors onto them, and can suspend idle Actors and restore durable data from snapshots. On resume it starts fresh containers with restored durable data. In-flight tool subprocesses and turn continuations need Guild-level cancellation, recovery and idempotency. Guild already has gVisor isolation. The incremental security opportunity is removing the Guild runner's Docker socket dependency and optionally adding microVM isolation; authorization, workspace boundaries, identity-scoped access, egress policy and exec approval still need equivalent enforcement. Snapshot storage adds data retention, access, lifecycle and backup concerns. Substrate Worker pods themselves require elevated privileges, and the microVM class needs KVM-capable nodes. [Substrate API guide](https://ate.dev/docs/reference/api-guide/), [security model](https://ate.dev/docs/security/security/) [Substrate repository](https://github.com/agent-substrate/substrate), [Substrate architecture](https://www.kagent.dev/docs/kagent/latest/about/architecture/agent-substrate/), [existing runner](../apps/server/src/sandbox/runner/manager.ts)

About 550–1,050 lines are for Actor lifecycle and transport, 450–1,000 for workspace, egress and deployment wiring, and 500–1,050 for migration and tests. The most concrete deletion is the 820-line runner plus parts of its client, Compose plumbing and tests. The sandbox-side environment and file/exec contracts account for much of the rest of the 1,760-line sandbox directory and are retained in this estimate.

Hosting the existing Guild turn workers is a second decision. The `TurnBackend` seam can remote the current loop while preserving Guild's source of truth. Fork IPC must become a network protocol for commands, stream events, and paired-machine dispatch. Single ownership and stale-worker fencing need to survive cluster placement, crashes and retries. A scoped Actor should receive only the task and credentials it needs. The roughly 867-line worker package is the upper bound on direct supervisor/IPC removal, with helpers potentially reused. Benchmark cold and resumed first-tool latency, idle memory and storage, workspace visibility across concurrent threads, and outcome reconciliation when an Actor dies mid-tool.

## kagent

**Recommended scope.** Register a small operator-managed specialist catalog. When Guild delegates work, bind an existing Guild child thread and run to a kagent session/task, stream results through Guild's event path, map cancellation to both systems, and retain Guild's parent wakeups and audit history. This fits predefined team/org specialists while Guild can keep dynamic workers and the personal Assistant's persistent inbox in its own harness. Approximately 350–750 lines cover task/session mapping and persistence, 450–1,050 cover streaming, identity, cancellation and policy, and 400–1,000 cover configuration and failure-path tests.

kagent compiles agent definitions into immutable revisions and ties each session to one revision and one Substrate Actor. This gives operators versioned GitOps, an agent catalog and standard A2A access. Guild agents and turns also have per-member context, per-turn model and tool policy, and account-scoped resources. Keep Guild thread admission and team/org access authoritative, and delegate only the scoped work. Keep Guild routines for persistent feed and continuation semantics. kagent's scheduled run creates a fresh session; it fits fixed prompts with independent results. kagent also separates cluster RBAC from runtime API authorization. [Core concepts](https://kagent.dev/docs/kagent/latest/about/core-concepts/), [scheduled runs](https://www.kagent.dev/docs/kagent/latest/agents/scheduled-runs/), [kagent architecture](https://kagent.dev/docs/kagent/latest/about/architecture/kagent/)

For main-chat hosting, BYO packages Guild's existing harness as a digest-pinned image implementing kagent's A2A gRPC contract. Guild must translate task state, streaming, and cancellation while preserving request IDs, queue/steer/withdraw/compact behavior, child results and recovery. The Guild journal can remain authoritative, but then kagent adds a parallel session/task lifecycle that has to be reconciled. The built-in kagent harness goes further by owning model/tool iteration and session state. Guild would need to rebuild or explicitly change approvals and their replay guarantees, dynamic CodeMode/tool discovery, mid-turn steering, compaction and event projection, attachments, and scoped machine execution. kagent exposes A2A cancellation and human-input handling, but those primitives alone do not match Guild's approval cards or nested Stop behavior. Guild's member WebSocket and persisted thread identity still need full adapters. [BYO contract](https://kagent.dev/docs/kagent/latest/agents/bring-your-own-agent/), [A2A example](https://kagent.dev/docs/kagent/latest/examples/a2a-agents/), [human input](https://www.kagent.dev/docs/kagent/latest/agents/human-in-the-loop/), [Guild execution contract](domain/003-execution.md)

The broad estimate assumes 1,400–2,800 lines for state migration and thread/event translation, 2,000–4,600 for tool/policy/interaction parity, 1,100–2,500 for runtime and deployment integrations, and 1,500–3,100 for tests and cutover logic. Removal assumes selected harness, chat, storage and worker code can retire after existing histories, active turns and clients transition. A revised product that accepts fixed revisions and A2A session behavior could cost less, at the expense of explicitly changing those interaction contracts. For version planning, the kagent v1.0.1 source pins Substrate v1.0.0, and the 1.0.x support table lists Kubernetes 1.35 for CI. Direct Substrate has a separate v1.0.1 release. Treat the kagent/Substrate pair as one upgrade unit. [kagent dependency pin](https://raw.githubusercontent.com/kagent-dev/kagent/v1.0.1/go/go.mod), [Substrate release](https://github.com/agent-substrate/substrate/releases/tag/v1.0.1) [Upstream version matrix](https://www.kagent.dev/docs/kagent/latest/reference/versions/)
