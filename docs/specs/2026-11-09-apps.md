# Apps

Status: phase 1 implemented (0.6.84). The rules live in
[004 Capabilities](../domain/004-capabilities.md) ("Apps") and
[002 Access](../domain/002-access.md).

## Problem

Agents can write HTML and the preview pane renders it, but a page is a
snapshot: whatever data it shows was pasted in when the Agent wrote it.
Members want pages that stay live — a pipeline board over HubSpot, an
incident view over Grafana — and that colleagues can open too.

Generated UI already rejected Tool calls from a block (OpenUI
`Query`/`Mutation`): they would run Tools outside a Turn, past Approvals.
An App has the same problem, plus two more: its code is untrusted page
script, and it is shared, so whoever opens it is not whoever built it.

## Decisions

1. **An App is HTML, not OpenUI.** It is a lasting, shared page, not a
   dialog in a transcript; models write good HTML, and the preview frame
   already exists. OpenUI stays the in-reply format.
2. **The page has no network.** It is served under a policy with an opaque
   origin, `connect-src 'none'`, local-only images and no popups or form
   targets. Its one channel is `postMessage` to the Guild client framing
   it.
3. **Data functions, not Tools.** An App declares named functions at
   publish: one Integration tool, fixed arguments, typed and bounded
   parameter holes. The page picks a function and fills holes; it never
   chooses the tool or the shape of its arguments. The manifest is the
   complete list of what the App can do.
4. **Every call acts for the viewer.** The viewer's Integration audience
   ceilings decide, as for a script call. Sharing an App never lends the
   author's reach, so sharing needs no review.
5. **Writes ask the viewer, every time.** A `write`/`admin`-class or
   `always_ask` tool needs a yes in Guild's own dialog (outside the page),
   and the server refuses the call without the flag that dialog sets.
6. **The publisher's reach is checked at publish.** A function that could
   not run for the publishing Member is an error the Agent fixes before
   anything is stored.
7. **Live list over the socket.** `app_list` carries the Apps a Member
   sees, on connect and on every change (`guild_apps` NOTIFY).

## Surfaces

- `publish_app` (agent tool, Files group): `path`, `name`, `description?`,
  `app_id?`, `functions?`.
- `GET /api/v1/apps`, `GET /api/v1/apps/{id}` (with each function as the
  viewer may call it), `GET /api/v1/apps/{id}/page_link`,
  `GET /api/v1/apps/{id}/page?v=&sig=`,
  `POST /api/v1/apps/{id}/functions/{name}` (`{params, confirmed}`),
  `PATCH /api/v1/apps/{id}` (`{visibility}`), `DELETE /api/v1/apps/{id}`.
- Page bridge: `guild.ready`, `guild.call(name, params)`,
  `guild.callRaw(name, params)` (`{data, text, meta}`), `guild.theme` and
  the `guild:theme` event.
- Desktop: `/apps`, `/apps/<id>`, an Apps rail entry.

## Later phases

- `guild.ask(prompt)`: a Turn with the App's Agent, through every normal
  gate.
- Per-App state (a small store the page reads and writes).
- Admin review before `org` visibility, if Apps start to matter.
- OpenUI programs as a second renderer behind the same bridge.
- Server-side caching of read functions per viewer, for dashboards left
  open in many tabs.
